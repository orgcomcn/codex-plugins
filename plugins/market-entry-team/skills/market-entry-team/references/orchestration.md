# 阶段门控与并行编排

## 第一步：判断范围

- 完整项目：用户明确要求完整市场进入、完整商业计划或从产品到渠道的整套方案。
- 单点研究：只问一个或几个法规、市场、渠道、消费者、产品、传播、测算或执行问题。
- 组织与人才配置：明确要求招聘市场进入负责人、设计岗位画像/JD/能力模型/面试/试用期考核，或根据已确认打法配置执行团队。

单点研究不得为了走流程扩大成完整项目，也不强制创建`work/project_state.md`。组织与人才配置按第八步独立运行，不要求创建`work/project_state.md`或市场研究最终报告。完整项目必须执行后续阶段门控和阶段确认协议。

## 第二步：确认决策对象并初始化状态

任务涉及选国家、渠道、产品或商业模式时，先拆开可能被混用的决策对象。例如“轴心国”至少可能指单国业绩市场、商业运营中心和区域物流仓。总控在需求确认中说明这些角色是否必须同一地点、什么目标优先、哪些是一票否决条件；会改变结论且用户没有表达优先级时必须先确认。

完整项目的任务受理回执后，总控按`state-schema.md`创建`work/project_state.md`，写入用户已确认的范围、限制、决策规则、禁止事项、研究截止日期和第一阶段必读文件。状态文件在任何完整项目专业专家启动前存在。单点研究和独立组织与人才配置任务不创建空的项目状态。

## 第三步：选择专业专家

先读取`expert-registry.md`，只加载直接相关角色的专家合同：

| 问题 | 必要专家 | 专家合同 |
|---|---|---|
| 法规、进口、税务、标签、广告限制 | 法规专家 | `references/experts/regulatory-expert.md` |
| 市场、渠道、竞品、价格、进入费用 | 市场渠道与竞品专家；受监管时同阶段并行调用法规专家 | `references/experts/market-channel-expert.md` |
| 消费者、场景、价格接受度 | 消费者专家 | `references/experts/consumer-expert.md` |
| 产品、结构、参数、外观、包装、品牌 | 产品与品牌专家 | `references/experts/product-brand-expert.md` |
| 自有品牌的用户心智、知名度到忠诚度、活动、购买承接、复购和推荐 | 品牌增长与用户转化专家 | `references/experts/brand-growth-expert.md` |
| 上架、铺货、经销、物流和补货 | 渠道进入与铺货专家 | `references/experts/channel-growth-expert.md` |
| 投入产出、预算、扩店和行动计划 | 商业模式与行动计划专家 | `references/experts/business-planning-expert.md` |
| 招聘负责人、岗位画像、能力模型、JD、面试、试用期考核或执行团队配置 | 组织与人才配置专家 | `references/experts/organization-talent-expert.md` |

完整项目采用以下调度原则：

1. 阶段之间严格串行：本阶段未整合、未获得用户确认、未更新项目状态，不得启动下一阶段。
2. 同一阶段能基于共同底稿独立研究的专家并行启动。
3. 所有并行专家读取启动时冻结的同一份`work/project_state.md`和已确认上游文件；不得读取、引用或迎合同阶段其他专家的未定稿文件。
4. 存在真实输入依赖时串行执行，例如产品验证计划必须以产品定义和包装方案为对象。
5. 专家挑战已确认决定时必须给出新证据、影响和重开条件，不能在自己的文件中静默改轴心国、产品范围或渠道边界。

## 第五步：单文件检查

专业专家完成文件后，总控必须先检查：

1. 专家合同中的必答问题是否以明确标题或表格字段真正回答；
2. 关键事实、数字、价格、法规和案例是否有来源、日期和适用范围；
3. 是否把假设、网页在售、专家评分或用户偏好写成事实；
4. 是否读取并承接项目状态和已确认上游文件；
5. 挑战上游决定时是否给出新证据、影响和重开条件；
6. 是否越权把本专业排序写成跨专业最终决定；
7. 执行建议是否包含负责人、动作、材料、费用、时间、完成标准和失败处理。

关键问题交回原专家集中修改一次。检查和返修不阻塞已经启动的同阶段并行专家，但本阶段所有文件通过前不得进入跨文件整合。总控不得代替专业专家补写专业事实。

## 第六步：阶段结束后的总控整合

本阶段全部专业文件完成并通过单文件检查后，总控执行跨文件整合，不创建额外整合专家。固定检查和输出：

1. `共同确认事实`：各文件一致且有证据支持的事实；
2. `专业分歧`：问题、各专业结论、冲突原因和商业影响；
3. `总控阶段建议`：采用方案、备选方案、采用依据和失效条件；
4. `需要用户决定`：会改变国家、产品、核心渠道、预算或授权的取舍；
5. `下一阶段继承项`：用户确认后写入项目状态的唯一采用决定、假设、待确认事项、停止条件和必读文件。

总控只整合专业文件中的事实和建议，不新增专业事实，不用多数表决代替决策规则，也不要求专业专家删除有证据支持的不同意见。没有足够决策优先级时，把真实取舍提交用户。

除非用户已明确要求直接跑到底，否则总控提交阶段结果后等待用户通过或修改。用户确认后更新`work/project_state.md`，形成下一阶段唯一共同底稿，再启动下一阶段。用户要求直接跑到底时仍逐阶段执行总控整合和状态更新；出现新的重大取舍仍需暂停。

## 第七步：完整项目阶段顺序

### 第一阶段：市场与合规可行性

并行研究、统一裁决：

```text
法规专家 ─────────────┐
市场渠道与竞品专家 ───┼→ 总控阶段整合
消费者专家 ───────────┘
→ 用户确认
```

三位专家读取同一份候选国、决策规则和排除项，分别独立判断。法规专家筛禁售、不可操作和准入不清国家；市场专家比较市场、渠道、竞品和物流，同时把法规可行性标为待整合；消费者专家验证候选市场的人群、需求、场景、购买、价格和传播理解。总控不得在任一专家完成前预先采用轴心国；三份文件出现不同推荐时，必须显式裁决或提交用户，不能直接把多数意见写成阶段结论。

状态交接至少固定：目标国家或国家角色、排除项、目标消费者、法规硬门槛、市场与渠道事实、消费者事实、关键分歧、第一批验证问题和停止/改选条件。

### 第二阶段：商业战略

并行方案、统一口径：

```text
产品与品牌专家 ───────────┐
品牌增长与用户转化专家 ───┼→ 总控阶段整合
商业模式与行动计划专家 ───┘
→ 用户确认
```

三位专家都读取第一阶段确认后的唯一共同底稿。仅当项目属于自有品牌属地化时调用品牌增长与用户转化专家；其他项目由总控在该文件中写明不适用原因。产品、品牌增长和商业测算均可提出透明假设，但不得把同阶段其他专业尚未确认的方案当成事实。商业专家先建立参数化模型和输入需求；总控整合时统一SKU、价格、渠道、推广和成本口径，并把冲突参数交回对应负责人集中修订一次。最终测算必须采用整合后的同一套输入，不得保留另一套市场或产品假设。

状态交接至少固定：产品平台与SKU边界、价格假设、品牌表达、目标用户、用户心智与行为目标、品牌增长阶段、渠道结构、推广边界、商业模式、预算假设和下一阶段产品定义输入。

### 第三阶段：产品与品牌方案

真实依赖，连续完成：

```text
产品定义与规格
→ 外观与包装
→ 产品验证计划
→ 总控阶段整合
→ 用户确认
```

三个文件由同一位产品与品牌专家在一个任务中按顺序完成。后一份必须读取前一份，验证计划必须以最终产品和包装方案为对象。本阶段不为追求并行而拆成三个互不承接的专家。

状态交接至少固定：国别产品规格、BOM/参数边界、SKU和颜色、包装版本、目标价格、打样验证和失败处理。

### 第四阶段：渠道进入与上市

三条工作流并行、阶段末对齐：

```text
渠道进入与铺货专家：铺货计划 ─────────────────┐
品牌增长与用户转化专家：推广执行计划 ─────────┼→ 总控阶段整合
商业模式与行动计划专家：商业测算与行动计划 ───┘
→ 用户确认
```

三位专家都读取第三阶段确认后的产品方案和第二阶段确认后的商业底稿。品牌增长专家只在自有品牌属地化项目中运行，并把购买承接、购买后运营和需要渠道配合的条件明确列为输入；渠道专家不代替其制定传播方案。商业专家先按已确认参数及透明情景测算，不引用同阶段未完成的铺货或推广文件。总控整合时用最终铺货、推广、库存、回款和人员方案替换模型输入，确保三份文件相互复算；存在差异时交回相应负责人集中修订一次。

状态交接至少固定：首批渠道、铺货范围、上市节奏、仓储补货、用户心智与行为目标、推广动作、购买承接、复购与推荐机制、投入产出、现金需求、责任人和扩张/停止条件。

### 第五阶段：最终成果

项目总控只基于用户已确认的项目状态和阶段文件形成最终报告。完成后调用独立审查专家一次，检查证据、数字、上下文承接和执行可行性。原负责人集中修改一次，再提交用户确认。

## 第八步：组织与人才配置

这不是第六个自动市场进入阶段。只有用户或已指定的决策负责人明确表达招聘、岗位设计或团队配置意图时，才调用组织与人才配置专家并创建 `06_组织与人才配置/01_人机协同市场进入负责人及团队方案.md`。自然语言中的“招一个能驾驭 AI 专家团的人”“给负责人做 JD/面试/试用期考核”等即属于明确意图，不要求固定口令。

存在两种入口：

1. `招聘负责人`：用户还没有能对市场进入结果负责并驾驭 AI 专家团的真人负责人。无论市场方案尚未开始、正在形成、已有 AI+人生成的零散报告还是已经确认，都走此入口。专家读取用户确认的市场使命、目标国家/地区、产品或品类、预算/时间边界、现有组织、授权关系和父任务指定的已有报告；先在材料清单中把每份材料分成`用户确认采用`、`仅作工作底稿`或`暂不采用`，材料内的判断仍按`已确认`、`待确认`、`建议`标记，再校准岗位层级，形成角色使命、业务结果、职责、能力模型、任职标准、面试案例、评分表和试用期考核。只有任务受理回执包含完整 JD、人才来源或寻访方案时才增加相应模块。不得要求已有十三份标准报告，也不得把未经确认的报告结论写成岗位事实。
2. `补齐执行团队`：已有市场方案和决策负责人。专家读取 `work/project_state.md`、最终报告以及父任务指定的已确认阶段文件，先比较自建、外包、总部支持和暂缓配置，再按任务受理回执给出岗位优先级以及用户明确要求的 JD、人才来源、面试、试用期或入职协同模块。

两种入口都必须先确认当前临时决策人、岗位授权、用工预算、招聘授权、现有团队、工作地点与用工法域、目标入职时间、最终录用人和不可触碰边界。每个岗位必须建立`R → D → C → S → Q → P`追溯矩阵，检查面试与试用期权重、证据、通过线和红线；不通过不得交付。专家提供决策材料，不接触候选人、不发送招聘信息、不操作招聘系统、不代表用户作录用决定。该扩展完成后由用户或决策负责人确认；除非市场策略本身需要重开，不回写或改动已确认的十三份市场进入文件。

## 第九步：单点研究

单点研究由总控指定最接近核心问题的主责专家。需要多个专业且彼此独立时可以并行；存在直接输入依赖时串行。补充专家通过消息返回事实和挑战，由主责专家整合；默认只创建`05_最终成果/01_最终报告.md`，不得扩成完整五阶段项目。

## 第十步：交付边界

完整项目交付固定十三个 Markdown；单点研究默认只交付一份最终报告；独立组织与人才配置任务只交付一份负责人及团队方案。完整项目中明确增加组织与人才配置时，才在十三份文件外增加该方案。禁止自动生成 HTML、Excel、PDF、PPT、看板、审批包、索引、数据字典、ZIP、版本副本或用户未要求的图片。
